Newsom Punts on SB 947 but Orders Two Agencies to Draft AI Kill-Switch Rules by November
BREAKING California Regulation
With SB 947 (the reintroduced No Robo Bosses Act) and SB 951 (a 90-day notice requirement before AI-driven layoffs) both still sitting unsigned on the Governor’s desk after clearing the legislature, Newsom sidestepped the fight over specific bills on 18 September and instead directed the Government Operations Agency and the Office of Emergency Services to design AI safety recommendations — external evaluators, kill-switch mechanisms and expanded incident reporting — due by 16 November. It follows his own Executive Order N-6-26 from May, which already has state agencies assessing AI’s workforce impact and updating California’s WARN Act guidance by 15 October. So what for a Deloitte HRSD practitioner: California is building the guardrails procedurally as much as legislatively, and a kill-switch requirement is not an abstract ask — ServiceNow’s own AI Control Tower shipped exactly that mechanism this month (see below), which means the platform side of compliance may arrive before the statute does. Track both dates on a client’s compliance calendar regardless of whether SB 947 gets signed: the WARN Act update lands in three weeks, the kill-switch recommendations seven.

No, the EU AI Office Is Not Inspecting Your Hiring Tool — Recruitment AI Rules Were Deferred to December 2027
NEW EU Regulation
A wave of vendor posts this month claimed the EU AI Office had begun inspecting automated hiring tools under “Article 50” — that is wrong on two counts. The AI Office supervises providers of general-purpose AI models, not businesses using a hiring tool, which answers to a national authority instead; and Article 50 is the general transparency duty that people must be told when they are dealing with an AI system, already in force for everything, not a hiring-specific inspection regime. The actual high-risk obligations for recruitment AI under Annex III — the ones with real conformity-assessment and documentation duties — do not bite until 2 December 2027, after the Digital Omnibus deferred them. So what for a Deloitte HRSD practitioner: useful to have on hand the next time a client’s legal team forwards a scary post about EU inspectors — the compliance clock has 14 months left to run, enough time to build the conformity documentation properly rather than scrambling, but it is not zero: Article 50’s transparency duty already applies today to anything an HRSD Virtual Agent or Otto skill says to a candidate.

AI Gateway Tool Catalog Baseline for Governed MCP

Idea

Turn on AI Gateway’s new MCP Tool Catalog and Kill Switch against a real set of connecting MCP clients, and find out exactly where the shipped feature stops and the custom User Criteria work has to start.

Intermediate ServiceNow HRSD · AI Gateway · AI Control Tower New Added 26 Sep 2026

Hypothesis

AI Gateway’s September GA shipped real MCP governance — a Tool Catalog that discovers and scores MCP tools at the individual-tool level, automated scanning for malicious behaviour and sensitive-data exposure, and a Kill Switch that revokes credentials through Okta and stops an agent mid-run — but a shipped platform feature is not the same as a configured one, and most HRSD instances will have it sitting inactive. A baseline configuration, tested against real connecting clients rather than assumed to work, is the fastest way to find out what the product now covers versus what still needs the bespoke User Criteria diffing from the earlier MCP permission red-team POC.

Approach

  1. Stand up the AI Gateway MCP Tool Catalog in a Zurich sandbox and connect two to three representative MCP clients: a Moveworks-style conversational assistant, a research-corpus client modelled on Galileo’s call pattern, and a bespoke internal agent built for a specific HR workflow.
  2. Run the automated scan against each and record what it actually flags — malicious behaviour, sensitive-data exposure, scope violations — against a held-out set of deliberately planted issues, so the detection rate is measured rather than assumed.
  3. Cross-reference against the manual User Criteria diffing built in the earlier permission red-team POC: does the Tool Catalog catch the same entitlement-leakage cases, a subset, or different ones entirely.
  4. Define a concrete Kill Switch trigger — an MCP tool reading beyond its declared scope, or exceeding a call-volume threshold — wire it up, and time detection-to-containment end to end.
  5. Produce a coverage map: what the shipped feature handles out of the box, what configuration closes the remaining gap, and what genuinely still needs custom engineering.

Deliverables

Configured Tool Catalog baseline with three connected test clients; detection-rate report against planted issues; Kill Switch runbook with measured containment time; coverage map versus the existing permission red-team findings; a one-page “what AI Gateway now covers for free” briefing for scoping future MCP engagements.

Client fit

Any client running or evaluating the HRSD MCP Server, especially one already fielding vendor pitches from research-corpus or copilot-style MCP clients such as Galileo; doubles as the governance evidence a risk or compliance team will ask for before approving a third-party MCP connection.

Effort & prerequisites

3–5 days, one practitioner with AI Control Tower and MCP Server Console access. Requires a Zurich sandbox with AI Gateway enabled and at least two MCP clients available to connect, one of which should be deliberately misconfigured to test detection.

Success signal

A documented case where the Tool Catalog catches a planted issue the team expected to need custom engineering for, and a documented case where it does not — both are useful, and together they turn “is AI Gateway’s governance enough” from a guess into an answer.

Automated-Decision Register for APP 1.8 Disclosure

Idea

Generate the privacy-policy disclosure Australia requires from 10 December 2026 out of live HRSD configuration — every program that makes or shapes a decision about a person, classified against the OAIC’s three-limb test, with the real human-override rate attached.

Intermediate ServiceNow HRSD · AI Control Tower · Scoped App Added 20 Sep 2026

Hypothesis

Most of what an APP entity has to disclose under APP 1.8 already exists as configuration inside its HRSD instance — assignment rules, auto-routing flows, Issue Auto Resolution, sensitivity detection, enabled Otto skills, Recruiter Workspace ranking, auto-decline branches — and a register generated from that configuration on a schedule is more defensible under OAIC scrutiny than a paragraph written by the privacy team from memory, particularly because the regulator has said generic wording will not do and that a rubber-stamp human does not take a program out of scope.

Approach

  1. Build a discovery job that enumerates candidate programs on the instance: business rules and Flow Designer flows that set assignment, priority, state or approval outcomes on HR case and lifecycle tables; Issue Auto Resolution and Virtual Agent topics that close or decline requests; every enabled Otto for HRSD skill and what field it writes to; Recruiter Workspace and Applicant Center ranking or screening steps.
  2. Walk each candidate through the OAIC’s three-limb test as a structured record: does the program make, or do something substantially and directly related to making, a decision; could the decision reasonably be expected to significantly affect rights or interests; is personal information used in its operation. Record the rationale and the reviewer.
  3. For every in-scope program, capture the human posture — advisory or determinative — and compute the actual override rate from case history over the last 12 months, so “a human reviews it” is backed by evidence rather than an assertion.
  4. Generate the APP 1.8 output in the categories the principle asks for: kinds of personal information used, kinds of decisions made solely by a program, kinds of decisions where a program is a key factor. Version it, date it, and make it regenerable on schedule.
  5. Produce the gap register: programs where the posture is unclear, where an override rate is effectively zero, and where a third-party model or MCP client receives the personal information — and map each to WA PRIS Principle 10 and the EU AI Act Article 14 human-oversight evidence so one register serves three regimes.

Deliverables

Discovery and classification scoped app; three-limb test record template with worked HRSD examples; generated APP 1.8 disclosure wording for one real instance; override-rate report; gap register with named owners and dates; short privacy-officer briefing on the difference between describing a tool and describing a decision.

Client fit

Every Australian client above the $3M turnover threshold running HRSD — which is all of them — with priority for WA public sector (Principle 10 already in force), regulated financial services, and any client whose HR AI touches recruitment screening or pricing-like decisions, the two edge cases the OAIC chose to publish.

Effort & prerequisites

6–8 days, two practitioners (one HRSD configuration, one privacy or Risk Advisory) plus privacy counsel review of the classification rationale. Requires an HRSD sandbox with Otto skills enabled and read access to 12 months of case history for the override-rate calculation.

Success signal

A generated disclosure that a client’s privacy officer accepts as the basis for their 10 December policy update, produced from live configuration, with at least one program the privacy team did not know existed surfaced by the discovery job.

Technology-Causation Record for Workforce Reductions

Idea

Capture whether AI or automation contributed to a role elimination at the moment the decision is made — because from 1 October a Connecticut WARN filing has to say so, under the Attorney General’s enforcement.

Intermediate ServiceNow HRSD · Workforce Events · Scoped App Added 16 Sep 2026

Hypothesis

Technology causation for a workforce reduction cannot be reconstructed reliably after the fact — the people who made the decision have moved on, the transformation programme and HR will disagree, and the disagreement is discoverable. Captured as a structured determination at decision time inside the HRSD workforce-change workflow, it costs almost nothing and produces a filing-ready answer that a general counsel will sign.

Approach

  1. Extend the position elimination, role redesign and restructure workflows so a technology-contribution determination is mandatory before the event can close, using a three-level taxonomy: no contribution, enabling contribution, direct substitution.
  2. Require a link to the specific programme, system or agent wherever a contribution is claimed, plus the evidence relied on and an attestation from the named accountable executive rather than from HR operations.
  3. Bind the determination to the position record and the lifecycle event so the attribution survives the departure of every person involved in making it.
  4. Build the filing assembly report: given a qualifying event of 50 or more separations inside 90 days, gather every contributing determination, surface inconsistencies between them before a regulator does, and output a filing-ready statement with its evidence trail.
  5. Add a quarterly drift report showing what proportion of workforce reduction is being attributed to technology, and test the whole thing against a reconstructed prior-year reduction to measure how much worse the retrospective answer is.

Deliverables

Scoped configuration for the determination and attestation; determination taxonomy with worked examples and edge cases; filing assembly report; decision-rights map naming who attests and who may not; general counsel briefing on the difference between a defensible attribution and a guess.

Client fit

Any client with Connecticut headcount above the 100-employee WARN threshold, and more broadly any multinational running technology-driven workforce change — the same record answers redundancy consultation, works council and EU collective dismissal questions, and the board-level question of how much reduction is being attributed to automation.

Effort & prerequisites

4–6 days, one HRSD practitioner plus employment counsel review. Requires an HRSD sandbox with workforce or position management configured and access to a representative set of prior reduction events for the retrospective test.

Success signal

A filing-ready statement generated from live records that employment counsel accepts without rework, and a measurable gap between the contemporaneous determination and the reconstructed one that proves the point to the client in their own data.

Advanced ServiceNow HRSD · Recruiting · AI Control Tower Added 11 Sep 2026

Hypothesis

Most of the Article 11 and Annex IV technical file for an HR screening system already exists inside the client’s HRSD instance as configuration — flow and integration topology, approval and override settings, ACLs and User Criteria, case outcome data — and a dossier generated from that live configuration on a schedule is both cheaper to produce and materially more defensible under inspection than a point-in-time document written by hand.

Any EU-exposed client running résumé screening, candidate matching, or AI-assisted recruitment in HRSD — and, because the deployer-side pattern generalises, multinationals facing Illinois HB 3773 notification duties, Colorado SB24-205 impact assessments, and the emerging NSW and Victorian instruments.

Effort & prerequisites

8–12 days, two practitioners (one HRSD/recruiting, one governance or Risk Advisory) plus EU counsel review. Requires an HRSD sandbox with Talent Acquisition and Now Assist enabled and access to a representative case and outcome dataset.

Success signal

A generated dossier that a client’s counsel accepts as the basis for an inspection response, produced from live configuration and regenerable on schedule, with the vendor-held gaps explicitly named rather than quietly assumed.

HRSD MCP Server Permission Red-Team

Idea

Prove whether knowledge-base User Criteria and COE security actually survive the hop when an external MCP client calls HRSD instead of a browser session.

Advanced ServiceNow HRSD · MCP Server Console · Zurich Added 22 Aug 2026

Hypothesis

A default HRSD MCP Server deployment using a shared service-account OAuth token collapses every knowledge-base User Criteria rule on the instance into a single omniscient identity, returning articles to callers who could never reach them through Employee Center — and per-user OAuth is the only configuration in which entitlements and the audit trail both survive the hop.

Approach

  1. Stand up the HRSD MCP Server in a Zurich sub-production instance via MCP Server Console, with HR Knowledge Search enabled.
  2. Seed a three-tier knowledge base: public articles, manager-only articles, and a genuinely sensitive tier scoped by User Criteria to a handful of HR partners (redundancy consultation, investigation procedure, executive remuneration).
